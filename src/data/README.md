# src/data/: the JSON the human pages consume

Generated by `npm run source` from the SRS repository in `source/`. **Do not edit these files**: change a record in `source/` and regenerate (see `source/README.md`). The same page files are also published for agents at `public/agents/<page>.json`.

**Pipeline-owned directories.** `src/data/` and `public/agents/` belong to the pipeline: every run rewrites them completely, and any file in them that the pipeline does not generate is removed. Do not put anything of your own there. The one exception is this `README.md`, which is carried over. A run that fails (invalid source, a copy-rule violation, a render diagnostic) changes nothing in the tree. `public/llms.txt` is generated the same way.

## Files

| File | What it is |
|---|---|
| `site.json` | The repository identity and the pages in navigation order. Use it for the header, footer and page titles. |
| `home.json`, `model.json`, `patterns.json`, `architecture.json`, `principles.json`, `projects.json` | One file per page, with the entries to render in order. |

## Page file

```json
{
  "page": "model",
  "title": "SemanticOps: model",
  "entries": [
    {
      "instanceId": "7f0c...",
      "type": "concept",
      "slug": "field",
      "fields": { "slug": "field", "title": "Field", "summary": "...", "body": "...", "example": "...", "spec_link": "https://..." },
      "relations": [
        { "type": "depends-on", "direction": "forward", "label": "Depends on",
          "targets": [ { "instanceId": "a1b2...", "slug": "record", "label": "Record and graduation" } ] }
      ]
    }
  ]
}
```

- `page` is the page key (`home`, `model`, `patterns`, `architecture`, `principles`, `projects`). `title` is the page container's title (a label for the file, not the display title: use `entries[0].fields.title`).
- **`entries` is in container order**, which is the order to render. Never sort or filter by type to recover a different order. The list is flat.
- **`entries[0]` is always the page's own `page` record** (`fields.title`, `fields.summary` for the meta description). The rest are its content.
- `slug` is the stable key: use it to choose a component or a diagram (`if slug === "capability-layering"`). It is unique across the whole site, so a record shared by two pages (the four projects, three principles) has the same `slug` and `instanceId` on both.
- `fields` are keyed by Field name. A key is absent when the record has no value. Values are plain strings; fields marked markdown below hold markdown source.
- `relations` is present only when the entry has relations. `type` is the canonical relation type, read source to target (an entry that `depends-on` another lists it under `targets`). A target `slug` is present when the target is rendered on some page, so it can be linked.

## Entry types and fields

The definitions, with their `aiGuidance`, are the source of truth in `source/package/`. In short:

| `type` | Fields (in order) |
|---|---|
| `page` | `title`, `slug`, `summary` |
| `section` | `title`, `slug`, `eyebrow`, `lede` (md), `body` (md). `eyebrow` and `body` are optional. |
| `concept` | `title`, `slug`, `summary` (one line), `body` (md), `example` (JSON text), `spec_link` (https URL). `example` and `spec_link` are optional. |
| `project` | `name`, `slug`, `kind`, `tagline`, `summary`, `audience`, `makes_possible`, `repository` (https URL), `licence` |
| `principle` | `title`, `slug`, `claim`, `explanation` (md), `pole_a`, `pole_b`. The two poles are optional and set together: a principle that is a held pair names its two sides. |
| `pattern` | `title`, `slug`, `pattern` (md, the general situation), `symptoms` (md, what goes wrong), `mechanism` (md, what SRS does), `case` (md, the small invented example a diagram draws). All required. Used on the `patterns` page. |

`route-step` records (`title`, `slug`, `target`, `why`) are not on any page: they are the lines of `llms.txt`, read from the `start-here` and `data` containers in `source/`.

`example` is display text: real JSON trimmed from the sample repository in `examples/meeting` (the extensions concept alone still quotes the specification), shown verbatim in a code block. It is not meant to be parsed. Markdown fields use plain CommonMark with inline code, lists, bold, links and fenced code.

## site.json

```json
{ "title": "SemanticOps", "purpose": "...", "pages": [ { "page": "home", "title": "Home", "summary": "..." } ] }
```

`pages` follows the root container's navigation order. `purpose` is the repository's identity statement.

## Stability

Page keys and slugs are keys: they change only by deliberate migration. Everything else is copy and may change whenever the owner edits a record, so components must not hard-code text that appears here.
